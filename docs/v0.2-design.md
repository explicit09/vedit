# v0.2 design: local repo, snapshots, linear history

The first surface where vedit is more than a diff tool. After v0.2 you can `init` a repo, `commit` timeline snapshots over time, `log` the history, and `show` what each commit changed.

## Scope

In:
- `vedit init` — create `.vedit/` in the current directory
- `vedit commit <timeline.otio> -m "msg"` — snapshot the file as a new commit on HEAD
- `vedit log` — walk commits from HEAD, newest first
- `vedit show <ref>` — render one commit's diff against its parent
- `vedit checkout <ref> -o <path>` — write the timeline at a commit to disk

Out (later):
- Multiple branches (only `main` in v0.2)
- Merging
- Remotes
- Media content hashing
- Editor adapters

## Storage layout

```
.vedit/
├── HEAD                # contains "ref: refs/heads/main" or a direct commit hash
├── refs/
│   └── heads/
│       └── main        # contains a commit hash
├── objects/
│   └── ab/
│       └── cdef...     # SHA-256 hash; first 2 chars are the directory
└── config              # author info, schema version
```

git-shaped, deliberately. Familiar to anyone who's looked inside a git repo. The two-character object-directory prefix avoids piling tens of thousands of files into a single directory.

## Object types

Two types in v0.2:

### timeline
The OTIO JSON snapshot, verbatim. Stored as gzipped JSON. The hash is computed over the canonical JSON form (recursive key sort, no whitespace) so two semantically-identical OTIO files always produce the same object hash.

### commit
```json
{
  "schema": "vedit.commit.1",
  "timeline": "sha256:abc...",
  "parents": ["sha256:def..."],
  "author": { "name": "tadies", "email": "tadiesm09@gmail.com" },
  "timestamp": "2026-05-06T07:42:00Z",
  "message": "Trim drone shot, add crossfade"
}
```

`parents` is an array. The initial commit has an empty array. Merges (v0.4) produce 2-parent commits.

## Hashing

SHA-256 of the canonical form of each object's content. Encoded as `sha256:` followed by lowercase hex.

Canonicalization:
- Recursively sort all object keys
- No whitespace
- UTF-8 encoded

This guarantees that the same logical object always produces the same hash, regardless of whitespace or key order in the original input.

## Encoding on disk

Each object is written as gzipped JSON. The file at `objects/ab/cdef...` is the raw gzip bytes. To inspect:

```
zcat .vedit/objects/ab/cdef... | jq
```

Reasons for gzip:
- Inspectable with standard Unix tools
- Same approach git takes for blobs
- Real compression on JSON (typically 60–80% size reduction)
- Forward-compatible: object type is encoded in the JSON, not in the filename

## Media references

Media files are not stored in the object store. The timeline's `media_reference.target_url` is preserved as-is. v0.2 records media by URL only.

A `fingerprint` field is reserved on each media reference for future content-addressed storage. v0.3+ may compute a SHA-256 of the file bytes when the file is accessible, store it in `fingerprint`, and use it as a stronger identity signal during diff matching. v0.2 leaves it `null`.

This matches how most teams already work — media lives on shared storage (NAS, LucidLink, S3) and vedit references it. vedit does not duplicate the media.

## CLI surface

```
$ vedit init
Initialized empty vedit repository in /Users/tadies/projects/cut/.vedit

$ vedit commit timeline.otio -m "Initial cut"
[main (root) 8a3c2f1] Initial cut

$ vedit commit timeline.otio -m "Trim intro, add crossfade"
[main b91e4d2] Trim intro, add crossfade

$ vedit log
b91e4d2  Trim intro, add crossfade  (HEAD -> main)
8a3c2f1  Initial cut

$ vedit show b91e4d2
commit b91e4d2  (HEAD -> main)
Author: tadies <tadiesm09@gmail.com>
Date:   2026-05-06 07:42:00

    Trim intro, add crossfade

  Trimmed "drone_shot_04" by 1.80s (in)
  Added crossfade between "title_card" and "drone_shot_04" (12 frames)

$ vedit checkout 8a3c2f1 -o earlier.otio
Wrote timeline at 8a3c2f1 to earlier.otio
```

`<ref>` accepts:
- A branch name (`main`)
- A short hash (`8a3c2f1`)
- A full hash (`8a3c2f1...`)
- The literal `HEAD`

## Ref resolution

`HEAD` is a file containing either:
- `ref: refs/heads/main` — symbolic, follow the named ref
- `sha256:abc...` — direct, no following

`refs/heads/<name>` is a file containing a single commit hash.

When we `commit`, we read HEAD, follow it if symbolic to find the current branch, write a new commit object with the previous head as parent, and rewrite `refs/heads/<name>` to the new commit hash.

## Author info

Read from:
1. `.vedit/config` if present
2. Git's `user.name` / `user.email` if `.gitconfig` exists
3. `$VEDIT_AUTHOR_NAME` / `$VEDIT_AUTHOR_EMAIL` env vars
4. Falls back to `unknown <unknown@local>`

Same fallback chain as git. Means `vedit init` doesn't force the user to configure anything before they can commit.

## What changes in vedit-core

New modules:
- `vedit_core::repo` — repo open/init, ref reading, head walking
- `vedit_core::object` — object encoding/decoding, gzip, hashing, canonical JSON
- `vedit_core::commit` — commit struct, log walker
- `vedit_core::timeline_io` — read/write OTIO files (renamed from `otio`, since we'll also write OTIO when we check out)

The diff engine is unchanged — `vedit show <ref>` calls `repo::load_timeline(parent)` and `repo::load_timeline(ref)` and runs the existing diff over them.

## What changes in vedit-cli

New subcommands: `init`, `commit`, `log`, `show`, `checkout`. Each is a thin wrapper around the core library functions.

## Test plan

For v0.2:
- Unit tests for canonical JSON (key reordering produces same hash)
- Unit tests for object roundtrip (write → read returns identical content)
- Integration test: init, commit twice, log shows both, show on second emits expected diff, checkout on first writes the original file
- Integration test: commit with no changes still creates a commit (intentional, like git)
- Integration test: ref resolution (full hash, short hash, branch name, HEAD)

## What this unlocks

After v0.2, `vedit show` becomes the natural surface for "review what an AI agent did to my timeline." The user runs the agent, the agent commits, the user runs `vedit show HEAD` and sees a structured English description of the changes. That's the agent feedback loop the project exists for.

v0.3 (branches) and v0.4 (merge) are then the obvious follow-ons.

## Open questions

- **Should `commit` accept stdin?** `cat timeline.otio | vedit commit -m "msg"` is convenient for agents producing OTIO programmatically. Probably yes.
- **Should there be an index?** Git has staging; vedit could skip it (commit takes a file directly). Decision: skip in v0.2. If users complain, add it.
- **Should we support multiple timelines per repo?** A real project might have V1 timeline and V2 timeline of the same edit. Decision: one timeline per repo for v0.2. Multiple-timeline support is a v0.3 question.
